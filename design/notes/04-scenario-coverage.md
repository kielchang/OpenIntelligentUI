# 怎麼確保 UI 能產出所有情境

它沒有「確保」，而是用四層機制把風險攤開：把需求空間切成有限分類、把產出端做成開放式、用文字規則約束品質、把失敗做成可見狀態。真正的情境覆蓋測試並不存在。

| 層 | 做法 | 原始位置 |
|---|---|---|
| 分類 | Jev 把每個請求判成 13 種型別之一，`text` 是萬用出口，資料不足就要求澄清而不是硬畫 | `apps/agent/src/visualization_router.py` |
| 產出 | 除表格走 A2UI 外，其餘 11 種全部交給 generateSandboxedUi 當場寫 HTML，所以任何能寫成網頁的情境理論上都做得出來 | 同上，renderer 對照表 |
| 約束 | 技能與系統提示規定每種情境的模式與品質：三種任務型態、計算器與比較與模擬與地圖與行程的寫法、三種圖型、輸入驗證、單位與假設標示 | `apps/agent/skills/*/SKILL.md`、`src/prompt.py` |
| 可見失敗 | 函式庫載入失敗要顯示訊息、地圖不能留白、NaN 要變成可操作的錯誤、非同步要有 loading 與 error 狀態、SVG 與 canvas 要有文字替代 | `prompt.py` 第 73 到 90 行、advanced-visualization 技能 |

幾個值得注意的設計決定：

- **覆蓋率來自分類的完備性，不是元件庫。** 13 種型別的描述刻意互斥且加上 `text` 兜底，所以任何請求都有落點。路由本身失敗時會把整輪標成可重試的錯誤，文件明寫「沒有靜默的 fallback」。
- **路由回傳 confidence，但沒有門檻。** 信心值只記錄在決策裡，沒有任何程式碼在信心低時改走文字或追問。
- **情境涵蓋靠模型自己。** 專案沒有情境矩陣、沒有 golden prompt、沒有模型輸出的評測。launch 影片裡的帳單分攤、3D 飛機、海岸地圖都沒有留下輸出，/gallery 裡那 11 個樣本是我依規範重建的。

**測試證明的是契約，不是情境。** 代理端 12 個測試檔驗的是路由只決策一次、壞決策會大聲失敗、續接時沿用決策、技能文件有沒有寫到規則、JS 範例沒有頂層 await。前端 19 個測試檔驗的是串流解析、渲染器階段、匯出、橋接驗證、金鑰閘門。CI 只有 lint、單元測試與建置的 smoke，沒有跑過真實代理的端到端。

要真的「確保」，缺的是三樣東西：

1. **情境矩陣與快照**：13 種型別乘上理解、比較、做工具三種任務，再加三種失敗情境，即無資料、CDN 失敗、窄版，每格一個 golden prompt 與一份產出快照。
2. **對實際產出跑自動檢查**：現有的文件契約測試可以直接延伸成對模型輸出的檢查，像是 schema 通過、html 無 style 與 script、有 role=status、錯誤路徑會顯示文字、不出現 NaN。
3. **每種型別跑一次真實代理的 Playwright**：把今天只做建置的 smoke 升級成用 fixture 金鑰實跑，截圖納入視覺回歸。

這三樣都不需要改架構，只需要把現有的「規則寫在文字裡」補上「產出被機器驗過」。
